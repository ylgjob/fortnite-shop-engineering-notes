Test Fortnite Cosmetic URLs After a Catalog Rebuild

November 23, 2026

Rebuilding a cosmetic catalog can change URLs even when no items were removed. Common causes are slugs generated from display labels and numeric identifiers based on list position. A reliable link needs to stay tied to the same cosmetic before and after an import.

Make the fixture change one thing at a time

Create a previous catalog with two fictional items, each with a fixed source ID. Save their detail URLs. In the next import, reverse their order, rename the first item, and give the second a different translated label. The saved links should still resolve to their original IDs. Test the response and the actual page title so a generic HTTP 200 fallback does not look like a pass.

Handle old URLs and real removals

If you improve a public slug, preserve the old route in an alias map and return a permanent redirect to the current preferred URL. The preferred page should identify itself consistently in its canonical tag and in the sitemap. Chain-free redirects matter when a label has changed twice.

When an item disappears from a new feed, check whether it is no longer in the provider's catalog or merely missing from that import. If you retain an archive record, explain its last-known status. If the record is genuinely gone and you have no equivalent, use an honest not-found response instead of routing everyone to a similarly named cosmetic.

Exercise existing bookmarks against a real catalog such as the SkinRotation cosmetic index. The test passes when the old URL leads to the right entity and the public navigation consistently points to its preferred address.
